Задача: проверь НАБОР требований целиком по ISO/IEC/IEEE 29148:2018, п. 5.2.6 и
IEEE 830-1998, п. 4.3. На входе — таблица фактов, собранная по всему документу (у каждого
факта есть дословная цитата), список требований и, если влез, полный текст.

Критерии:
- set_consistent — противоречие между двумя местами документа: требование против критерия
  приёмки или примера, основная часть против спецификации API, цель против нефункциональных
  требований, разные значения одной величины, разные названия одного компонента;
- set_complete — пропущенное поведение, без которого набор нельзя реализовать или проверить;
- set_feasible — набор в целом невыполним из-за сочетания требований;
- set_comprehensible — термины и сокращения не определены, понятны только автору;
- set_validatable — нельзя подтвердить, что набор удовлетворяет заявленной цели;
- ranked (IEEE 830 4.3.5) — указаны ли важность (приоритет) и стабильность (ожидаемая
  изменчивость) требований. Не больше ОДНОГО замечания на документ уровня minor, с пустым
  requirement_ids; в explanation назови, чего нет: важности, стабильности или обоих;
- traceable, modifiable — трассируемость и удобство изменения набора;
- security — риски ИБ, видимые только при взгляде на набор.

Как искать противоречия: сравни факты ВНУТРИ каждой темы и факты смежных тем (например,
period_dates и examples, api_status_errors и examples, enablement_defaults и
trigger_conditions, actors_components во всех разделах). Противоречие — это когда два факта
не могут быть верны одновременно или дают разный ожидаемый результат на одних и тех же
входных данных. Проверь каждый пример и критерий приёмки по правилам: получится ли по
правилам именно тот результат, который в нём ожидается.

Чек-лист полноты (замечание, только если документ это не описывает и случай проходит
порог существенности из общих правил):
- изменение настройки в середине периода: что с уже накопленным и уже совершёнными
  действиями, возможно ли повторное срабатывание;
- включение функции или изменение условия, когда условие уже выполнено;
- граничные значения и их включительность;
- отмены, возвраты, частичные и отложенные операции, другая валюта;
- сбои, повторы, идемпотентность, момент фиксации результата;
- для каждой операции записи — как читается сохранённое состояние;
- для каждого значения в сообщениях и расчётах — откуда оно берётся;
- для каждого кода ответа — объявлен ли он и есть ли пример; для каждой ветки логики —
  есть ли ответ и критерий приёмки.

Правила ответа:
- Для противоречия приводи ОБЕ цитаты (из разных мест) — с одной цитатой замечание будет
  отброшено. Цитаты копируй из поля «цитата» фактов или из текста документа дословно.
- В requirement_ids перечисли все затронутые требования из списка.
- Не повторяй дефекты, которые видны в одном требовании без сравнения с другими: их
  проверяет другой агент.
